At a glance

A marketer enters just a brief (what to advertise) and a channel (social / search ads / email), and this RAG tool returns ad copy built on verified EV technical info and the brand's voice. So the AI doesn't pretend to know and make things up, it first looks up (retrieve) the material it needs, then writes (generate) from it.

Brands: Tesla as the main one, plus Hyundai · Chevrolet. The heart of the demo is showing that the same brief comes out in a different voice for each brand.

Building a librarian. When a question comes in, this part picks only the right ones out of the Step 1 ingredients. There are two ways to search, depending on the kind of ingredient.

  • Exact lookup (SQL) — Numbers and tables are pulled straight out by name. No AI involved.
  • Search by meaning (vector search) — Text needs "pieces with a similar meaning," so we use embedding + FAISS.

All the code lives in retrieval.py (Step 2).

2-1 · DB lookup functions Done

get_specs("Model Y") (Step 2-1) — Returns that model's single row from the specs table. Numbers in the copy (range · charging speed · price) come only from this function. One row per model, so the answer is always the same.

get_examples("Tesla", "Model Y", "social") (Step 2-1) — From the ads table (Step 1), picks only same-brand · same-channel · approved ads and returns the top 2 by performance. Ads for the same model come first; if there aren't enough, it fills in with other models from the same brand. → These become the few-shot examples shown to the AI in Step 3 as "write it like this."

Performance metric: ctr (click-through rate) for social · search, click_rate for email.

2-2 · Chunking + indexing Done

You can't hand the AI a manual that's hundreds of pages long, so this step cuts it into small pieces and builds a card box you can search by content. python retrieval.py build-manual → index/chunks.faiss, index/chunks.json (Step 2-2, local only).

  1. Read PDFs — Only the 9 full manuals. The quick reference guides (QRG) are left out because they overlap.
  2. Clean up (clean_page) — Tidy whitespace, remove the header repeated on every Chevrolet page, remove figure labels in the Hyundai PDFs (1C_WindowOpenClose), and drop tables of contents and pages under 30 words.
  3. Cut (chunking, windows) — 200 words per chunk, with the last 40 words of each chunk repeated at the start of the next (overlap). That way a sentence cut at a boundary keeps its context. Why 200: the embedding model MiniLM only reads up to about 256 tokens (the class code uses 800).
  4. Guides split by subheading — One chunk per ## / ###; model-specific sections also get a model label.
  5. Labels (metadata) — Each chunk gets brand · model · source file · page number. The brand filter in Step 2-3 relies on these.
  6. Turn into numbers (embedding) — Prepend "Tesla Model Y owner's manual:" and convert to 384 numbers. That way a search for "Model Y charging" hits the Model Y pages.
  7. Save to FAISS — An index for quickly finding similar meanings. For vectors scaled to length 1, the dot product = cosine similarity.

Result: 8,953 chunks = manuals 8,887 (Hyundai 3,268 · Tesla 3,059 · Chevrolet 2,560) + guides 66 (22 per brand).

Rules shared by all three brands

Numbers and claims (Claims and Numbers)

  1. Every number comes from the spec database (ev.db). Range · battery · charging power · 0–60 · price · warranty are never written from memory.
  2. Feature descriptions come from that model's manual (→ feature cards).
  3. Don't mix DB numbers and manual numbers in one claim. If they differ, use only the DB number.
  4. Range is always "estimated" + the disclaimer "Actual range varies with conditions and driving habits."
  5. Charging times come with their conditions (charger type, starting · ending battery %). If those are unknown, leave the time out.
  6. Prices use "starting at" + model year.
  7. No comparisons that name competitors.

② brand filter — Open only our section

  • Pick Tesla and you only see Tesla cards · the Tesla guide. The guides' rules conflict with each other, so they're never mixed (→ Supercharger · V2L · Super Cruise in the brand guides above).
  • Even if another brand's car name comes up, that brand's cards aren't pulled. Example: Hyundai with "write that our frunk is bigger than Model Y's" → 0 Tesla cards. This blocks competitor-comparison copy.
  • For industry, each brand gets the same number of picks (k=5 → 2 per brand) → so no single brand's voice takes over the results.

③ search — Pulling similar cards (hybrid search)

  • Search by meaning (embedding, MiniLM) — Finds matches even when the words differ but the meaning is the same, like "charge quickly" and "fast charging."
  • Search by words (TF-IDF) — So questions where the exact wording matters, like "zero emissions," don't get missed.
  • The two rankings are merged with RRF (reciprocal rank fusion) — a bit like combining the class rankings of two sections into one overall ranking. The plan called for BM25, but TF-IDF fills the same role. (Word search was added after seeing 85% on the holdout during 2-4 grading)

2-4 · Answer set + recall measurement In progress

The librarian's exam. We ask questions whose answers we already know and grade whether search brings the right card into the top 5 (Step 2-4, eval_retrieval.py).

Must-follow rule — Filter cards by car name first, then drop the name from the question when comparing
  1. If the question contains one of our brand's car names (e.g. "How fast does Model Y charge?") → first keep only the Model Y cards.
  2. Then, when measuring similarity, delete "Model Y" from the question and compare using just "How fast does it charge?".

Why? All 18 Model Y cards contain "Model Y," so if the name stays in, all 18 look similar and the actual "charging" card gets pushed down. The name was already filtered in step 1, so step 2 only looks at which feature is being asked about. We found this on question C04 during grading and added it to the router rules (decision log in project.md).

4. 22 judge answer sentences — finalize Decision needed

Related step: Step 4-2. This is the answer sheet for grading the judge (fact-checker). Right now Claude's draft is provisionally accepted (data/judge_labels.json, 15 supported · 7 unsupported).

What this step checks — When the LLM writes something that isn't backed by the feature cards or specs it was given for that ad, can the judge catch it? So the verdict rule isn't "is it true?" but "was this in the cards and specs the LLM was given when it wrote that ad?" Even a true statement counts as unsupported if it wasn't in that material.

What we found

  • The LLM really does write unsupported content — 6 of the 7 unsupported sentences came straight from the Step 3 LLM (home charging, a welder, One-Pedal, and so on — none of it in the cards it was given). The remaining one (J22) is a trap we wrote on purpose.
  • The judge's first rule was too strict — 64% agreement with the answers. It wrongly flagged 8 of the 15 supported sentences (rounded specs like "about 7 seconds", usage scenes like "when you camp", even decorative words). It also mistook disclaimers for claims.
  • We fixed the judge's instructions — only new features, behaviors, devices or numbers count as unsupported; rounding, usage scenes and decorative words are fine; disclaimers are left out and only the body is checked → 86% agreement.
  • But 86% is inflated — we tuned the rule while looking at the same 22 sentences. Once the answers are final, we need to re-measure on new sentences to see the real number.
  • It works in the real pipeline — on an Equinox EV email the judge flagged "Level 2 charging overnight" and "trailer hitch space" as unsupported, and after the rewrite there were 0 unsupported sentences (Step 4-3).
